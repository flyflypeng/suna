# Suna 会话记录（2026-02-09）

## 助手

**目标说明**
- 在 Suna 中进行“通过浏览器点击网页”的自动化，核心依赖是内置的 Browser Tool，它使用 Daytona 沙箱里的本地 Stagehand 服务来驱动浏览器动作并返回截图与页面状态。

**配置概览**
- 后端必须配置 Supabase 与 Daytona，此外必须提供 GEMINI_API_KEY 以初始化 Stagehand。
- 不需要额外安装浏览器驱动；沙箱镜像内置 Chrome、VNC、以及本地的 browserApi 服务。
- 计费相关的 STRIPE_* 可留空，不影响浏览器自动化。

**必需的后端环境变量**
- Supabase
  - SUPABASE_URL
  - SUPABASE_ANON_KEY
  - SUPABASE_SERVICE_ROLE_KEY
- Daytona（沙箱）
  - DAYTONA_API_KEY
  - DAYTONA_SERVER_URL（默认 https://app.daytona.io/api）
  - DAYTONA_TARGET（如 us）
- LLM（用于浏览器动作推理）
  - GEMINI_API_KEY（Browser Tool 必需，用于 Stagehand 的 act/extract）
- 参考清单见自托管文档的环境变量表。

**浏览器自动化工作原理**
- Browser Tool 启用状态：在默认配置中已开启。
- 调用链：
  - 创建或唤醒 Daytona 沙箱
  - 沙箱启动 supervisord，拉起浏览器与本地 browserApi（Stagehand）服务
  - Browser Tool 检查 8004 健康状态，不健康则用 GEMINI_API_KEY 调用 /api/init 完成初始化
  - 执行动作接口：navigate/act/extract/screenshot，通过 curl 调用本地服务
- browserApi 服务实现细节（端口 8004）。

**前端与运行必备**
- 前端环境变量（用于运行 UI，不影响纯后端自动化）：
  - NEXT_PUBLIC_SUPABASE_URL
  - NEXT_PUBLIC_SUPABASE_ANON_KEY
  - NEXT_PUBLIC_BACKEND_URL（默认 http://localhost:8000）
- 完整前端清单参考自托管文档。

**落地步骤**
- 准备环境文件
  - 复制 backend/.env.example 至 backend/.env，填入上述 Supabase、Daytona、GEMINI_API_KEY
  - 复制 frontend/.env.example 至 frontend/.env.local，填入前端所需键
- 启动后端 API 与后台 worker
- 首次运行时让 Suna 创建沙箱（Browser Tool 会懒加载沙箱）
- 执行一次浏览器动作作为验证：
  - 使用浏览器工具的 navigate 和 act 方法
  - act 涉及上传元素时需传 filePath 字段，以防触发系统文件对话框无法处理
- 验证健康与截图：
  - Browser Tool 会自动返回当前页面的 url/title/screenshot 链接
  - 如服务未就绪，工具会返回调试信息（进程/端口）

**可选增强**
- 在线查看沙箱界面：暴露 6080（noVNC）或 8080（沙箱 Web）端口获取预览链接。
- 如果希望改用云端 Browserbase 而非本地 Stagehand，可参考示例项目的 BROWSERBASE_API_KEY/BROWSERBASE_PROJECT_ID，但默认 Browser Tool 走本地服务即可。

**常见问题排查**
- 缺少 GEMINI_API_KEY：Browser Tool 会直接报不可用提示。
- 8004 未监听或初始化失败：Browser Tool 会返回健康检查与初始化的 JSON/端口信息，按提示重试或检查 Daytona 配置。
- STRIPE_WEBHOOK_SECRET 等留空：对浏览器自动化无影响，可忽略。

## 助手

**核心区别**
- 前端选择的模型用于对话和工具编排（思考、规划、调用工具），属于“代理层”的大脑。
- 浏览器自动化用的是 Stagehand 的内部推理模型，专门负责“看页面、定位元素、执行点击/填写/抽取”等动作，和对话层分离。

**为什么必须配置 GEMINI_API_KEY**
- Browser Tool 在执行任何浏览器动作前会强制检查 GEMINI_API_KEY；未配置直接拒绝执行。
- 沙箱里的本地 browserApi（Stagehand 服务）固定使用模型 google/gemini-2.5-pro，并且需要把 API key传进去初始化（/api/init）。
- 这套模型只服务于“act/extract”的页面交互与内容抽取，与前端的聊天模型相互独立，所以前端默认模型即使可用，也不会自动供给 Stagehand 使用。

**这样设计的原因**
- 行为推理与视觉/DOM 操作需要稳定且对 UI 任务调优的模型，当前集成里选择 Gemini 2.5 Pro 来提升点击成功率、表单填写准确率与提取质量。
- 将“聊天模型”和“浏览器动作模型”解耦，能更灵活地在对话层用你偏好的模型（如 Anthropic/OpenAI），同时在动作层使用对 UI 更可靠的模型。

**如果不想用 Gemini**
- 目前实现是硬编码 Gemini，因此仅配置前端默认模型不会影响 Stagehand。
- 可以改造为可配置：
  - 在后端配置里加入例如 STAGEHAND_MODEL_NAME/STAGEHAND_MODEL_API_KEY；
  - 修改 browserApi 接收 provider+api_key 并用对应的 modelName 初始化；
  - 修改 Browser Tool 将这两个值传给 /api/init；缺省时回落到 Gemini。
- 这样就可以让“浏览器动作模型”与“前端选择的聊天模型”保持一致或由你自由指定。
